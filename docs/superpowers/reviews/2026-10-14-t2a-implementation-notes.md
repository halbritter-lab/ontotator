- Task 9 (Codex review finding 3): `save_search_event` checked that an event ID was new in any project without a lock, and imports serialised only against other imports, while the primary key `(project_id, event_id)` cannot enforce a global ID; a local save in project A and an import into project B could both see the ID as absent and both insert different content under it (unscoped lookups then raise `AMBIGUOUS_SEARCH_EVENT`, and a walk append overwrites every copy) -> both paths now hold a transaction-scoped advisory lock, `SEARCH_EVENT_IDENTITY_LOCK`, from the check to the commit: local saves take it shared (their IDs are a fresh uuid4 or a hash over workspace and mutation, so they need not wait for each other), an import with search events takes it exclusively. One lock for all IDs instead of a lock per ID (or hashed buckets) keeps a large import at one lock and needs no sorted acquisition; local saves wait only while an import with search events runs, and imports are serialised globally anyway. Lock order: `import`, `project`, the identity lock, then search event rows (`FOR UPDATE`); `append_search_event_candidates` creates no ID and takes no identity lock, and no caller combines an append and a save in one transaction. A global identity table with a unique constraint was not chosen: it needs a migration and a backfill for an invariant the lock already gives. Covered by `tests/test_pg_repository.py::test_an_import_racing_a_local_save_of_its_event_id_is_refused` and `::test_a_local_save_racing_an_import_of_its_event_id_is_refused` (the second operation is released only once it waits for a lock or has finished).
