## Findings

### R1 — P2: Include the frontend eligibility gate in repeated translation correction

**Plan location:** Task 10, lines 221 and 229–230; dependency on Task 7, lines 186–194.

Task 10 correctly identifies the backend allocation gap and requires correction of an accepted corrected translation through normal assignment APIs. Its implementation/test scope does not include the frontend gate that independently prevents the same journey. Task 7 touches `assignmentUI.tsx`, but specifies hierarchy and presentation, without changing this eligibility rule or assigning a later integration step.

**Source evidence:** `frontend/src/admin/assignmentUI.tsx:28–30`, `canReviewSelection`, rejects both document and variant metadata with `translation_status === "accepted"`. `TaskSelect` at lines 37–38 then omits Translation review entirely. `frontend/src/admin/AssignDialog.tsx:14–19` uses that predicate to populate the task selector and line 31 repeats it in the Assign button guard. `DistributionDialog.tsx` uses the same helpers. The backend equivalent is `src/ontotator/assignments/eligibility.py`, `check_variant_assignable`, which Task 10 already proposes changing.

**Effect:** Even after a successful API-level v2→v3 regression, a lead using the app still cannot allocate the next correction from accepted v2. This is the exact normal-user gap documented in protocol line 579; direct API success does not close it.

**Plan amendment:** Give Task 10 explicit ownership of the corresponding assignment UI eligibility/action and its handoff from Task 7. Add a focused frontend interaction test and the real-API browser path: accepted corrected v2 → intentional new correction review assignment → reviewer submits v3. Preserve role/language checks, linear ancestry and stale-parent rejection. A deliberate correction action may be appropriate; this finding does not require indiscriminately making every accepted translation ordinarily assignable.

### R2 — P2: Assign the user-facing entry points for the new workflow actions

**Plan location:** Tasks 10–11, lines 221–241, and Task 12, lines 245–253.

The product design includes lead-started consolidation, reviewer confirmation that an original update needs no translation change, and lead handling of reports/extended holds/clean restart. The packages describe domain/API behavior and tests, but do not explicitly assign the frontend actions and destinations needed to perform several of these operations. Task 10 lists backend files only. Task 11 lists an annotator `ProblemReportForm` and editable/read-only task entry points, but no lead handling surface. Task 12 promises actionable dashboard destinations without naming where these new actions will live. Task 14's integrated journey cannot substitute for implementation ownership.

**Source evidence:** `frontend/src/tasks/TaskEditor.tsx:48–73` retains an `AssignmentOpenRequest` and opens the current assignment; lines 91–99 only resume existing proposal-review target-set rounds. This is not a lead submission-selection/consolidation flow. `src/ontotator/application/workspaces.py:160–181` explicitly obtains document proposals rather than other members' submissions. `src/ontotator/application/translation_reviews.py:49–70` records a translation review, while `_context` at lines 159–170 resolves the exact historical original; this existing workflow does not supply the new source-update-specific no-change action. The plan correctly acknowledges these backend differences, so an existing UI cannot be assumed to acquire the new behavior automatically.

**Effect:** Packages can satisfy their listed backend scenarios while users still cannot initiate consolidation, open the intended new round, clear a source-change obligation without changing text, or complete lead report handling. A warning link would lead to inspection without an action that resolves its cause.

**Plan amendment:** Add a compact action-to-surface/owner table for Tasks 10–12, with authorization and exact record identity carried by each destination. At minimum cover lead selection of frozen consolidation inputs/reviewer; opening/resuming the resulting work round; reviewer no-change confirmation for a specific original update; and lead report resolution, hold extension and restart agreement. Reuse the tree, task editor, translation-review view or dashboard detail as suitable; no new visual design or broad new screen is required by this review. Add a few focused frontend interactions and explicit real-API browser cases for consolidation and no-change confirmation. Keep ordinary proposal review visibly distinct.

## Existing gates remain gates, not newly missing requirements

The following are already acknowledged in the plan and should not be reported again as absent product decisions:

- **Round identity and immutable compatibility:** The record table, contract checkpoint and remaining-detail item 2 explicitly gate Tasks 10–12. `domain/workspace.py` currently has a strict `WorkspaceKey` without round identity; `domain/results.py::latest_submissions` groups complete serialized origins; `storage/repository.py:2315–2348` restores prior submissions when creating a draft. The plan correctly requires a reviewed migration/format strategy instead of an optional field and an empty-screen approximation. Verify ordinary history/export-import continuation alongside empty restart persistence.
- **Transactional hold/restart enforcement:** Refine the already requested state/permission contract to cover existing writes and stale sessions, not just new report endpoints. `authz/scoped.py:128–145` currently blocks mutations for submitted assignments; lines 176–188 revalidate around assignment locking. `storage/repository.py:2472–2513` distinguishes authority checks, receipt replay and new mutations. Define the linearization of hold/restart versus an in-flight save/submit, deny new writes to held/abandoned work, and ensure replayed old responses cannot replace the active round in the client. A focused two-session test here is more useful than a broad extra suite. This is a concrete acceptance criterion for the existing checkpoint, not a proposal to alter historical receipts.
- **Consolidated scientific export:** The checkpoint and Task 12 already require a distinct T1 representation. `exchange/t1.py:542–547` and `686–689` currently produce an individual set; `exchange/jobs.py:165–187` currently obtains the old latest-individual export inventory. Do not infer readiness from Task 1's provenance repair. Exact selection, frozen input closure, contributor/provenance semantics and the export receipt need review before this new mode is implemented.
- **Strict policy and immutable Unresolved proposals:** Remaining-detail item 1 expressly leaves confirmation metadata versus an exposed rule conflict open. `domain/project_rules.py::rule_violations` treats a default marker as not chosen in strict mode. The plan preserves the real blocker and the original Unresolved outcome rather than promising an automatic replacement. Resolve this contract before claiming the strict-policy workflow complete.
- **Warning scope, first-use preferences and symbols:** The plan explicitly leaves precise cause coverage/empty exports, preference migration/defaults and exact non-SVG assets for bounded decisions. These do not reopen the confirmed lead authority, per-language selection, conscious warning override, personal persistence or stable layout requirements.
