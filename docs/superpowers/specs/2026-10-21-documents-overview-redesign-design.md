## Problem

The lead reads a row's state from a "Next step" sentence and an "Owner" word, while the pipeline has three stages that each have their own state. A text that waits on a reviewer, one that waits on the lead and one that is finished look alike except for the sentence. Nothing marks what changed since the lead looked last. The filter bar has four selects plus five more under "More filters", and the segments sit in a second bar. Choosing a final result expands the whole row (stage cards, submissions table, More) and the actual choice sits at the bottom. When a text is corrected after annotation started, open work on the old version stays open silently, the row asks to "Assign annotation" again as if nothing existed, a submitted annotation can only be carried by the annotator finding "Continue from this submission", and a changed source text has no step at all.

## Relation to `feat/lead-followups`

The branch (worktree `.worktrees/phase0-implementation`, merge base `a66469d`, 9 commits, not merged) implements the follow-up spec: F1 lead self-correction of a rejected or queried translation (`LeadCorrectionPanel.tsx`, migration `0017_lead_corrections`), F2 exact Progress links (FD10 repeatable `step`/`stage`/`plan`, `final=any`, `paused`; FD11 Progress counts equal Documents queries; FD12 `bar.finals`), F3 all filters in batch and selection summary, F4 display names in problem reports, F5 Resolve focuses the Translation block.

This spec **rebases on it**: implementation starts after `feat/lead-followups` is merged to `main`. Interaction:

- **Filters:** FD10 repeatable parameters (OR within, AND across) are the base of the facets; this spec adds more repeatable parameters of the same form. Every FD11 Progress link stays valid; its parameters that have no facet (`step`, `stage`, `paused`, `owner`) render as removable chips ("Step: Assign annotation"). The FD11 contract test (count = `bar.shown`) stays green and gains the Done count.
- **Export link:** FD12 `bar.finals` keeps driving "Export final results…" (moved next to the tabs' "Updated" line).
- **F1 / F5:** Resolve options keep rendering inline under the row (not in the expansion). The F1 lead-correction panel moves from the Translation review stage block (which leaves the expansion) into that inline Resolve panel; F5's focus target becomes the inline panel's heading.
- **F4:** PersonRefs on reports feed the second line of "⏸ Paused" and "Waiting on".
- **F3 / VD21:** the row-level `rows` parameter extends the F3 filter set; both live in `DocumentRowFilters`.
- **Migrations:** `0019_documents_overview` with `down_revision = "0018"` (VD20; renumber rule there).
- **Conflicts:** `DocumentsPage.tsx`, `DecisionBar.tsx`, `ExpandedRow.tsx`, `StageBlocks.tsx`, `document_row_page.py`, `document_rows.py` are touched by both; WP O0 starts from the merged state.

## New-item signal

### Last visit (VD6)

- Table `documents_visits(user_id, project_id, baseline_at, last_seen_at)`, primary key `(user_id, project_id)`.
- `POST /projects/{key}/documents/visit` (lead only) is sent when the Documents page mounts (not on refetch, tab or filter change). Server: if no record, insert `baseline_at = last_seen_at = now` (first visit: nothing is NEW); else if `now − last_seen_at ≥ 30 min`, set `baseline_at = last_seen_at`; always set `last_seen_at = now`. Returns `{baseline_at}`. Returning from the editor within 30 minutes keeps the baseline, so NEW badges survive a round trip.
- **NEW** on a row = its next step is lead-owned (kind `decision` or `assign`, or the row is undecided) **and** `row.others_activity_at > baseline_at`. `others_activity_at` is the newest event on the row not caused by the viewer: import, correction, review decision, submission, problem report, hold, assignment by another lead, system carry (V8). Acting on the row removes NEW only by changing its state; otherwise it stays for the visit.
- Rows endpoint: `DocumentRowView.new: bool` and `others_activity_at`; computed from the stored baseline (no client parameter).

### Navigation counter

"Documents (3)" in the current project's section (`Shell.tsx:94`) = `needs_decision` of that project (undecided rows included, V10), for leads only. `GET /projects/{key}/documents/summary` → `{needs_decision}`; the shell loads it like `useOpenTaskCount` (once, on window focus, every 60 s, and on a `documents-changed` event fired after own actions). ### Agreement (V9)

- **Finding:** an annotation of a submission snapshot in an editable layer (the same set `finding_count` counts).
- **Match:** same `layer_id`, same `term_id`, equal context (`axes` values equal, a missing axis equals its default; `modifiers` equal as sets) and either (a) both have mentions and some evidence segment of one overlaps some segment of the other by at least one character, or (b) both are spanless (`document_level` or no mentions).
- **Context difference:** (a) or (b) holds with the same term, but the context differs.
- **Pairing:** submissions compared must be on the same document version. Two submissions: maximum one-to-one matching, exact matches first, then context differences, ties broken by the largest overlap, then annotation order. `n` = exact pairs + context pairs + unmatched of A + unmatched of B; "k of n match" with k = exact pairs; "Only here" = unmatched per submission. Three or more: clusters built in submission order (each finding joins at most one cluster, one finding per submission per cluster, compared with the cluster's first finding); k = clusters with an exact finding from every submission, n = clusters, "Only here" = clusters with only that submission's finding.
- Computed on the server (pure `domain/agreement.py`), never stored.
