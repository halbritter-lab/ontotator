## Rules decided in this spec

> **Update 2026-10-27 (decision A103):** R3's refusal (`MODIFIER_AS_FINDING`) became a warning. A modifier term as a finding's own term is accepted (some name a finding, e.g. Stillbirth HP:0003826) and listed as the acknowledgeable submit warning `modifier_as_finding`; ontospan reports `modifier_as_annotation` as a warning; a unanimous group is a normal match. Allowed roots still refuse.

| ID  | Topic                             | Rule                                                                                                                                                                                                                                                                                                                                                                                                |
| --- | --------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| R1  | Identity                          | One modifier per term per finding. A modifier is `(term_id, segments)`; `segments` is 0..n non-overlapping segments (T1 F6). The UI links one contiguous span per action; imports may carry more.                                                                                                                                                                                                   |
| R2  | Where modifiers are allowed       | Only on annotations in layers whose ontology pin has the T1 profile `hpo-phenotype`. Other layers refuse `MODIFIERS_NOT_SUPPORTED`.                                                                                                                                                                                                                                                                 |
| R3  | Modifier terms as findings        | Impossible for new data: create, set term and adoption refuse `MODIFIER_AS_FINDING`. Old data and other proposal sources are flagged: a blocking open item in the editor ("Turn into modifier…"), a blocking submit rule, and a group kind `modifier_as_finding` in consolidation.                                                                                                                  |
| R4  | Agreement (`compare`, Final cell) | Unchanged rule V9: modifiers count as part of the context **as a set of term ids**; modifier segments are ignored (like spans, which only need to overlap).                                                                                                                                                                                                                                         |
| R5  | Consolidation grouping and W1     | `groups()` compares modifiers **with their segments** (exact offsets, like spans and cues). Any difference gives the kind `modifiers_differ`, so the group is not `match`, is never taken over automatically, and W1 "All findings match" is not offered.                                                                                                                                           |
| R6  | Auto take-over                    | Requires identical modifier sets **including segments** (follows from R5). Justification: an automatic take-over hides the decision; a difference the consolidator never sees would silently pick the earliest person's version, and W1 and consolidation must agree (acceptance fixes T7).                                                                                                         |
| R7  | Union                             | No union option: the consolidator ticks single modifiers (DN-1), so the union of several people's modifiers is several ✓; one term with different segments are exclusive variants (DN-2, R1). Rule in "Consolidation scenarios", selection rule.                                                                                                                                                    |
| R8  | Provenance                        | No per-modifier provenance. The consolidated annotation keeps the existing provenance (`merged`, `source_refs` = every input of the group); the decisions' `ConsolidationMark` records which choice was made. T1 `Modifier` stays `{term_id, segments}`.                                                                                                                                            |
| R9  | Text versions                     | Carrying and re-anchoring map modifier segments with the same `TextMap` as evidence. A segment that cannot be mapped makes the whole finding _needs review_ (reason `changed_modifier_segment`); no silent loss.                                                                                                                                                                                    |
| R10 | Frequency                         | Allowed everywhere a modifier is allowed, tagged "Cohort term" in every list, chip and choice; an acknowledgeable submit warning (same mechanism as unconfirmed values); counted in the export report.                                                                                                                                                                                              |
| R11 | Content hash                      | `modifiers` is omitted from the annotation content while empty (precedent `axes_defaulted`), so every existing snapshot version, decision hash and submission id stays unchanged. No SQL migration.                                                                                                                                                                                                 |
| R12 | Two of one kind (M8)              | Exclusive classes are the Severity (HP:0012824) and Onset (HP:0003674) subtrees. ## Data model and content hash

- **`domain/annotations.py`:** new `Modifier(BaseModel, extra="forbid")` with `term_id: str` (CURIE) and `segments: list[Segment] = Field(default_factory=list, exclude_if=lambda v: not v)`. `Annotation` gets `modifiers: list[Modifier] = Field(default_factory=list, exclude_if=lambda v: not v)`. The `validate_and_sort` validator refuses a repeated `term_id` (`InvalidAnnotation`), sorts modifiers by `term_id`, sorts each modifier's segments and refuses overlapping segments within one modifier.
- **`annotation_content`:** adds `"modifiers": [m.model_dump() for m in annotation.modifiers]` only when non-empty (empty segments are omitted from each modifier). Existing hashes stay unchanged (R11); a golden test pins three existing snapshot versions and one submission id.
- **`snapshot()`:** also validates modifier segments against `document.text` (`validate_segments`), so a modifier segment out of bounds is refused like a mention.
- **Segments overlap rules:** a modifier segment may overlap the finding's own mention ("schwere Krampfanfälle" as mention, "schwere" as Severe) and another finding's mention; the same text may be linked as a modifier to several findings ("beidseits" → Bilateral on two findings).
- **Term ids** are stored as the primary id (alternative ids resolve, as for `term_id`).
- **`ConsolidationMark`** (`domain/review.py`) gets `attached_to: str | None = Field(None, exclude_if=lambda v: v is None)` (scenario S18). Decision hashes stay unchanged.
- **Storage:** snapshot payloads are JSONB (`AnnotationSnapshotRow.payload`); no migration. `decode_snapshot` reads old payloads unchanged.
- **Exports that serialise annotation content** (review export, edit-log export, final content) show `modifiers` once non-empty; no consumer may assume a closed key set (checked in M1).

## Validation (server side)

All checks use the layer's pinned ontology. A cached per-pin classifier (`ontology/registry.py`: `modifier_kind(term_id) -> "modifier" | "cohort" | None` and `exclusive_class(term_id) -> "severity" | "onset" | None`, computed once per ontology sha256 from the HP:0012823, HP:0040279, HP:0012824 and HP:0003674 subtrees) serves validation, search and grouping.

| Where                                                      | Check                                                               | Result                                                                                                      |
| ---------------------------------------------------------- | ------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `add_modifier`, resolve `choice.modifiers`, T1 import      | term not under HP:0012823 or HP:0040279 (ontospan `not_a_modifier`) | `MODIFIER_NOT_ALLOWED` (import: `T1_INVALID` with the ontospan code)                                        |
| same                                                       | unknown / obsolete term                                             | `UNKNOWN_TERM` / `OBSOLETE_TERM` (as for findings)                                                          |
| same                                                       | term already on the finding                                         | `DUPLICATE_MODIFIER` (import: ontospan `duplicate_modifier`, WP O1)                                         |
| same                                                       | Frequency subtree (ontospan `cohort_frequency`)                     | accepted; warning at submit (R10), in the import and export reports                                         |
| `create_annotation`, `set_term`, adoption of a proposal    | finding term is a modifier term (ontospan `modifier_as_annotation`) | `MODIFIER_AS_FINDING` with `{term_id}`; no new standalone modifiers                                         |
| submit (`rule_violations`, new rule `modifier_as_finding`) | a snapshot's term is a modifier term (old data)                     | `PROJECT_RULE_VIOLATION`, blocking: the T1 export would fail on it (`exchange/jobs.py:_validate`)           |
| submit warning list (today `AXIS_CONFIRMATION_WARNING`)    | a modifier from the Frequency subtree                               | warning `cohort_modifier` added to the same acknowledged list and digest; error code kept for compatibility |
| `add_modifier`, resolve `choice.modifiers`, T1 import      | a second modifier of the same exclusive class (R12)                 | accepted                                                                                                    |
| submit warning list                                        | a finding with two modifiers of one exclusive class (R12)           | warning `exclusive_modifier_class` in the same acknowledged list and digest                                 |

`rule_violations` stays pure: the caller passes the set of modifier-term findings (from the classifier).

## Editing commands

New commands in `application/editing.py`, each a draft mutation with a new snapshot, `checked_layer_ids` cleared for the layer and `_update_decision_replacements` (so an edit of a `cons-…` annotation reads _edited_ in consolidation):

| Command                 | Payload                                                  | Effect                                                                                                                                                       |
| ----------------------- | -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `add_modifier`          | `{annotation_id, term_id, segments?: Segment[]}`         | Adds one modifier. If the term is already there without segments and `segments` are given, they are linked instead (the attach flow's "already there" case). |
| `set_modifier_segments` | `{annotation_id, term_id, segments: Segment[]}`          | Links (replaces) or, with `[]`, removes the modifier's text span.                                                                                            |
| `remove_modifier`       | `{annotation_id, term_id}`                               | Removes the modifier.                                                                                                                                        |
| `convert_to_modifier`   | `{annotation_id, target_annotation_id, link_span: bool}` | Old data (R3): deletes the standalone modifier finding and adds its term (with its first mention's segments when `link_span`) to the target. One mutation.   |

`create_annotation` and `set_term` refuse modifier terms (R3); `set_term` keeps the finding's modifiers. Deleting a finding deletes its modifiers. Contract: `contracts/openapi.json`, `frontend/src/api/generated.ts`, `client.ts`.

## Search subtree filter

- `SearchRequest` (`ontology/provenance.py`) gets `within: list[str] | None = Field(None, max_length=8)`. When set, only terms in the subtrees of these roots (root included) are returned. The filter runs **before** the `k` cut: the service asks the engine for a widening top-n (k × 10, then all) until `k` hits survive or the ranking is exhausted, so a restricted search never returns fewer hits than exist. The browse route uses `within` as its roots.
- The shuffle seed includes `within` only when it is set, so seeds of existing searches stay unchanged; the stored search event records `within`.
- `SearchCandidate` gets `role: "finding" | "modifier" | "cohort"` from the classifier, for layers pinned with `hpo-phenotype` (else always `finding`).
- "+ Add modifier…" searches with `within = ["HP:0012823", "HP:0040279"]`. The normal search is unrestricted and shows modifier hits with the tag "Modifier" ("Cohort term" for Frequency).
- `allowed_roots` (stored on the pin, unused by search today) restricts finding terms only (T1 F5). If a later project filter applies it to search, the modifier subtrees stay searchable for the attach flow.
- Subtree id sets are cached per ontology sha256 and root (the classifier cache); no new search index.

### Attach mode (from the text, E-a)

1. The annotator marks "schwere"; the prefilled search shows Severe with the tag "Modifier".
2. Enter (or click) on a modifier hit for a **new mark** does not create a finding. It starts the **attach mode**, built on the existing attach-mention banner of the text pane (`attach-mention-banner`, `role="status"`): "Attach Severe: click its finding in the list or in the text (↑ ↓ Enter in the list). Esc cancels." with the button "Cancel (Esc)". The pending mark and its `PendingMarkBar` stay.
3. **Targets:** every finding of the annotator in an editable `hpo-phenotype` layer: its row in the findings list (accessible name "Attach Severe to Seizure", spanless findings included) and its marks in the text (title "Attach Severe to Seizure"). The **nearest** finding in the same sentence (pure helper `sentenceBounds(text, offset)` in the new `editor/modifiers.ts`: boundaries at `.`, `!`, `?` followed by whitespace, and at line breaks; ordered by character distance between the marked span and the nearest mention segment; on a tie the finding **after** the mark wins: adjective before noun, "schwere Krampfanfälle") is focused in the list (its row shows "Attach Severe here" with the key hint Enter) and its marks are framed (`run--framed`).
4. **Inspector** while the mode is on: heading "Severe" with the tag "Modifier", the line "HP:0012828 · “schwere”", "Severe describes a finding. Choose it in the findings list or in the text.", "Nearest in this sentence: Seizure · “Krampfanfälle”", the primary button "Attach to Seizure" (key hint Enter) and "Cancel" (key hint Esc).
5. **Attach:** a click on a target row or mark, Enter on the focused row (↑ ↓ move between the target rows) or "Attach to Seizure" sends `add_modifier` with the mark as segment (as adjusted with its edge handles: the pending mark stays resizable in the mode); the mode ends, the finding is selected and its new chip is focused, polite status "Attached Severe to Seizure. Next: mark more text, or add another modifier with “+ Add modifier…”."
6. **Esc** (anywhere while the mode is on) or "Cancel" ends the mode and discards the pending mark as before (`discardPending()`, focus to the text after the mark). Marking other text ends the mode and replaces the pending mark (as today).
7. The chosen finding already has Severe: without span → the attach links “schwere” to it (status "Linked “schwere” to Severe of Seizure."); with another span → the click or Enter only focuses that target and the inspector shows "Seizure already has Severe (“sehr schwere”). Attaching replaces its text span." with the primary "Replace text span", which sends `set_modifier_segments` (`add_modifier` would refuse `DUPLICATE_MODIFIER`).
8. No finding in the sentence: no nearest; the inspector shows "No finding in this sentence. Choose one in the findings list or in the text." instead of the "Attach to …" button; focus goes to the first target row.
9. No target at all (no own finding in an editable `hpo-phenotype` layer): the mode does not start; the inspector shows "Severe is a modifier. Create the finding first, then add Severe under Modifiers." with the single button "OK" (discards the mark).
10. "Change term" of an existing finding shows modifier hits `aria-disabled` with "Modifier — add it under Modifiers instead."; the tree browser follows the same rules.

## Agreement and grouping (pure domain)

- **`Finding`** (`domain/agreement.py`) keeps `modifiers: frozenset[str]` (term ids, used by `compare` and `_assign`'s exactness, R4) and gets `modifier_spans: tuple[tuple[str, tuple[Span, ...]], ...] = ()` (sorted `(term, segments)`, used by `groups`) and `standalone_modifier: bool = False`.
- **`finding_of`** (`application/document_row_panel.py`) fills both from the annotation (today `frozenset()`) and `standalone_modifier` from the classifier; `findings_of` and `round_members` pass it through. The final panel and the consolidation read obtain the classifier for the project's pins.
- **`groups()`:**
  - New kind `modifiers_differ`: within one term, members' `modifier_spans` differ; in a `term_differs` group, any two members' `modifier_spans` differ (the modifier row compares all members, see S11).
  - New kind `modifier_as_finding`: a member is a standalone modifier finding. It excludes `match` and combines with `partial` and the others. Clusters of standalone modifier findings never take part in the term merge (they would offer a modifier as the term).
  - No majority field on `Group`: the "(2 of 3)" label of DN-3 is per modifier and is counted in the client from the members' modifiers (they are all in the read view); never a computed set (M9).
  - `compare()` results stay unchanged for findings without modifiers (regression tests).
- **W1:** `_all_match` uses `groups()`, so modifier differences, segment differences and standalone modifier findings all prevent "All findings match" (R5).

## Consolidation

### Backend

- **Read** (`application/consolidation.py`): each member gets `modifiers: [{term_id, term_label, kind: "modifier" | "cohort", segments: [[start, end], …]}]`; `_added` findings carry modifiers too. Labels are filled by the route like `term_label`.
- **Resolve** (`application/consolidation_resolve.py`):
  - `ResolveChoice` gets `modifiers: list[ModifierIn] | None` (`{term_id, segments}`), the explicit final list. Omitted: the span member's modifiers (as `note_from_input_id`). Validated as in "Validation"; the server does not require that the list comes from the members, so "Edit values…" can also add a modifier everyone missed.
  - `keep` and the automatic take-over: the kept member's modifiers. `leave_out`: none. (`keep_both` no longer exists: a group resolves to exactly one finding.)
  - `ResolveCommand` gets `attach_to: str | None`, allowed only with `leave_out` on a `modifier_as_finding` group (S18).
- **Edited:** the consolidated content hash covers modifiers, so an editor edit of a `cons-…` annotation's modifiers reads _edited_ (S21).

### Frontend

- **Comparison table** (`ComparisonTable.tsx`, rows from `groupModel.ts` `comparisonRows`): a row "Modifiers" (shown when any member has modifiers) after "Text". When `modifiers_differ` is set (term sets **or** segments differ, DN-4 A) it is a conflicting row (conflict mark with the hidden text "Conflict:"); otherwise one grey line "Severe “schwere”, Recurrent “wiederholt” (all agree)".
- **Choices in the Modifiers row (DN-1, DN-2):** each person's cell lists their modifiers as separate ✓ toggles (`aria-pressed`), "Severe “schwere”", "Recurrent", "Severe (no text)" (spanless while another person linked that term); a person without modifiers has the toggle "No modifiers". The selection rule ("Consolidation scenarios") decides what one ✓ presses or releases; there is no union line or union column, no "Text of {term}" row, no preselection and no computed majority or intersection option (M9). "(2 of 3)" follows each toggle that more than half of the members hold identically (DN-3 A). Cohort terms carry the tag "Cohort term" (text). When the chosen modifiers contain two of one exclusive class, the row shows the warning "Two severities" / "Two onsets" (R12). No "·" anywhere on the consolidation screen (DN-10 A, DESIGN.md rule): visible "Severe “schwere” (2 of 3)", accessible name "Take Severe “schwere” from Ana Weber for Modifiers (2 of 3)", "Take No modifiers from Cem Arslan for Modifiers".
- **Resolving (DN-11 A):** a group with a conflicting Modifiers row is not resolved by the last ✓ (several ✓ are allowed). Once every conflicting row has a choice, the primary "Keep" appears; nothing is saved until "Keep", which sends `choose` with `choice.modifiers` = the chosen modifiers; afterwards "Change" reopens, as today. When Modifiers is the only conflicting row, the "Whole finding" row ("Take Ana's finding") is hidden; when other rows conflict too it stays as today: "Take {name}'s finding" resolves at once and takes that person's values **and** modifiers.
- **Result line (DN-5 A):** appends ", modifiers: Severe “schwere”, Recurrent “wiederholt”" / ", no modifiers" / ", modifiers not chosen yet"; the collapsed "decided: …" line names them the same way ("decided: Seizure (HP:0001250), Present, Patient, Current, modifiers: Severe “schwere”, Recurrent “wiederholt”").
- **Cross-link hint:** when a person linked the same modifier term and segment to a finding of another group, the row shows "Ben Roth linked “schwere” (Severe) to Hypotonia." with a link to that group (computed client-side from all groups).
- **Edit values…** (offered on groups without a conflicting field, incl. reopened agreed groups and partial groups) gains the Modifiers section with chips and "+ Add modifier…".
- **Standalone-modifier card (S18, DN-8 B):** it resolves only with "Attach to a finding…" or "Leave out" (no Keep, Edit values… or Other term…); "Edit in editor…" stays (it navigates, it does not resolve). With no resolved finding in the sentence, "Attach to a finding…" is `aria-disabled` with the reason "No resolved finding in this sentence yet."
- **Text pane (DN-7 A):** modifier segments are drawn in the person's lane with the lane's own line style (lanes are told apart by line style, lane 4 is double, so the editor's `run--modifier` double underline is not reused here) and explained in words (title and hidden text "Severe, modifier of Seizure (Ana Weber)"; several people: "(Ana Weber, Ben Roth, Chris Lee)"); the selected group frames its members' modifier segments.
- **Summary:** the group header no longer lists kinds (it shows "n fields to decide" / "agreed" / "decided: …"); a Modifiers conflict counts as one field to decide.

## Consolidation scenarios

People A = Ana Weber, B = Ben Roth, C = Cem Arslan, in round order. Text: "Seit 2 Wochen wiederholt schwere Krampfanfälle und eine Muskelhypotonie." Terms: Seizure HP:0001250 ("Krampfanfälle"), Hypotonia HP:0001252 ("Muskelhypotonie"), Focal-onset seizure HP:0007359, modifiers Severe HP:0012828 ("schwere"), Mild HP:0012825, Recurrent HP:0031796 ("wiederholt"), Neonatal onset HP:0003623, Frequent HP:0040282 (Frequency). `{Severe “schwere”}` is a modifier set; "no span" means the modifier has no segment. Unless stated, axes, spans, cues and notes are equal. "Agreement" is the Final cell's `compare` (R4): _match_, _context difference_ (complete cluster, not exact) or _only here_. W1 needs every group to be `match`.

**Selection rule (DN-1, DN-2, replaces the earlier U-rule):** each person's cell in the Modifiers row lists their modifiers as separate ✓ toggles; a person without modifiers has the toggle "No modifiers". A modifier is identical when term **and** segments are equal. Pressing a toggle presses the identical modifier in every other cell; pressing it again releases it everywhere. One term with different segments (or with and without segments) are exclusive variants: pressing one releases the others, which then read "other text chosen" (a finding has each term once, R1). All "No modifiers" toggles press together and are exclusive with every real modifier toggle. The row has a choice once any toggle is pressed; the chosen modifiers are exactly the pressed ones ("No modifiers": none). The union of several people's modifiers is simply several ✓ (no union line, no union column, no "Text of {term}" row); any combination of the members' modifiers can be chosen, one variant per term. "(2 of 3)" follows each toggle (incl. "No modifiers") that more than half of ≥ 3 members hold identically (DN-3 A). The group then resolves with "Keep" (DN-11 A).

Further rules the table relies on:

## Experiencer "Family member" (M7)

- **Values:** `domain/axes.py` `ExperiencerType = Literal["patient", "family_member", "other"]`; `STANDARD_CLINICAL_AXES` and the `hpo-phenotype` template (`domain/profile_templates.py`) list `["patient", "family_member", "other"]`. The editor follows the profile order: Patient · Family member · Other person (labels exist in `editor/axisLabels.ts`; three options fit the segmented control).
- **Meaning** (guidelines text): `family_member` = the finding is stated for a relative ("Mutter mit Epilepsie"); `other` = another person who is not a relative.
- **ontospan:** already supports it at the pin: `profiles/hpo.py` `AXES["experiencer"] = ("patient", "family_member", "other", "unknown")`, and `phenopacket.py` omits such findings with the report counter `omitted_family`. `check_t1_profile` therefore accepts the new option; T1 import accepts it where the project profile has it (else `T1_UNKNOWN_AXIS_VALUE`, as today); export writes it as is. **No ontospan change and no lossy mapping.**
- **No old data (M11):** the option is simply part of the standard profile and template; no migration and no special handling for locked profiles or existing projects. Leads can hide the value (`hidden_axis_values`).
- **Agreement and consolidation:** just another axis value (values row, majority label).
- **Defaults:** creation defaults stay `patient`.
- **Fixtures and seed:** `examples/t5-acceptance/profile.json` (the seed's profile) gets the option; existing test fixtures (`tests/fixtures/smoke-profile.json`, `tests/layered_fixtures.py`) stay unchanged to keep golden hashes; new tests use their own profile. `tests/test_axes.py` covers the new `STANDARD_CLINICAL_AXES` (its `config_sha256` changes; nothing stores it).
