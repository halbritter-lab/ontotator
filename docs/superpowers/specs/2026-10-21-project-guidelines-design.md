# Project guidelines: versioned document, in-task reading, version per submission: design

Status: design proposal, 2026-10-21. Scope and the core decisions (G1 to G9) approved by the user 2026-10-20; the user's answers of 2026-10-21 are recorded as G18, G19, G23 and G25 (no existing submissions or productive data; names of members who have not seen the current version; withdrawing a version). G20's rule that exports carry guideline references only, never texts, was set by the orchestrator 2026-10-21 as the simplest safe default after the user was undecided; it can be revised later. The other detailed choices (G10 to G17, G20 to G22, G24, G26, G27) were made while writing this spec and are open to the user's veto before implementation. No open questions remain. Not implemented.
Builds on: [T3 admin design](2026-10-14-t3-admin-design.md) (project settings, roles, audit), [problem reports](2026-10-19-problem-reports-design.md) (toolbar entry pattern, shared UI rules), [quick fixes and export](2026-10-19-quick-fixes-and-export-design.md) (final export archive), [lead follow-ups](2026-10-20-lead-followups-design.md) (migration `0017`). Mockups: none; the copy and structure below are binding.

## Goal

Every project can carry its annotation guidelines inside Ontotator: one text document per project, versioned, uploaded by the project lead. Annotators and reviewers read the version in force from any task without leaving it and learn once, without being blocked, when a new version arrives. Every submitted result states the guideline version it was made under, and exports carry that version, so a result can always be read against the rules that applied to it.

## Current state (verified in code, main `69db7d0`)

- **Data:** a project has two free fields, `guideline_url` and `guideline_version` (`storage/tables.py:103-104`, created in `migrations/versions/0005_admin.py:52-53`). There is no guideline text, no history of versions and no per-user state.

### Rationale

- **Renderer (G12).** There is no Markdown library in the frontend. `react-markdown` turns Markdown into React elements, so no HTML string is ever injected and React escapes all text. Raw HTML in the source is not rendered by default (no `rehype-raw`), and its default `urlTransform` drops `javascript:`, `vbscript:` and `data:` URLs. Alternatives: `markdown-it` and `micromark` produce HTML strings and need `dangerouslySetInnerHTML` (safe only as long as their options and a sanitizer stay correct); server-side rendering with `markdown-it-py` (present only as a transitive dependency) would need a Python sanitizer (`nh3`) and still inject HTML. The cost of `react-markdown` + `remark-gfm` (tens of KB gzipped) is paid only when a guideline is opened or previewed, through `React.lazy`. Additional element rules (component overrides): links open in a new tab with `rel="noopener noreferrer"` and only for `http`, `https` and `mailto`; relative links and in-document anchors render as text with the target shown; images are never loaded (rendered as the link "Image: {alt}" to the URL), so a guideline cannot pull remote content or track readers; headings are shifted by one level inside the panel (`#` becomes `<h3>` under the panel's `<h2>`). `defaultUrlTransform` returns `""` for an unsafe URL, so the link override renders text whenever `href` is empty (never `<a href="">`, which would point at the current page). GFM footnote references and back-references are in-document anchors and therefore render as text (accepted limitation).
- **Server-side "seen" (G16).** Annotators switch browsers and machines; a local flag would re-show the notice on each device and would give the lead nothing. The server record is cheap (one row per user and version), makes the notice exactly once, and lets the lead see how far a change has reached and whom to remind (G23). It is not an acknowledgement: nothing is blocked and no audit event is written per read.
- **No fallback after withdrawing the current version (G25).** Falling back to the previous version would put rules back into force that the lead had deliberately replaced, without anyone deciding so, and new submissions would be stamped with them; the withdrawn version may even have fixed an error in the previous one. "No guideline in force" is visible (Settings says so, the task button disappears), new stamps honestly record nothing, and restoring earlier rules is one deliberate upload of that file (G10). The cost is a short gap in which annotators have no in-task guideline; Settings prompts the lead to close it.
- **What a withdrawal deletes (G25).** The purpose is a file that must not stay readable. Its text, file name and change note therefore live in a separate deletable table (`guideline_contents`) and are not copied into the append-only audit log (`guideline.upload` records number, kind, size and hash only). The hash stays so existing `guideline_ref` values remain verifiable references.

**`guideline_reads`** (mutable; `GRANT SELECT, INSERT, UPDATE`)

| Column                  | Type                    | Notes                                            |
| ----------------------- | ----------------------- | ------------------------------------------------ |
| `project_id`, `version` | FK `guideline_versions` | PK part                                          |
| `user_id`               | bigint, FK `users.id`   | PK part                                          |

| `opened_at`             | timestamptz, null       | first time the panel showed this version         |

Writes are upserts that only fill a null timestamp (first time wins).

**Version stamp on results** (nullable columns on append-only tables, added by the owner; no row is updated):

- `submissions.guideline_version integer NULL`, FK `(project_id, guideline_version)` → `guideline_versions(project_id, version)`.
- `translation_reviews.guideline_version integer NULL`, same FK.

The stamp is a column, not part of the `Submission` payload: the payload format (`ontotator-submission/v2`/`v3`, `extra="forbid"`) and the submission identity stay unchanged, and imported submissions are untouched.

**Upgrade:** create the four tables and the two stamp columns; drop `projects.guideline_url` and `projects.guideline_version`. There is no data to convert (G18).

**Downgrade:** re-add the two columns empty (nullable); drop the stamp columns and the four tables (uploaded texts are lost; the downgrade docstring says so).

## Backend

New module `application/guidelines.py` (`GuidelineService`), storage rows in `storage/guideline_tables.py`, and the read helpers used by repository and export code (`current_guideline_version`, `guideline_facts`) in `storage/guidelines.py`: the storage layer never imports `application`, and `application` modules import `storage.repository`, so `storage/repository.py` importing `application/guidelines.py` would be circular.

- **Upload:** the route reads the multipart file in bounded chunks (as `api/ontology_routes.py` `_upload_files`) and refuses with `GUIDELINE_TOO_LARGE` after at most 262,144 + 4 bytes, so an oversized file is never read whole; then validate extension (G11), size, UTF-8, NUL, emptiness, change note (G13); take `pg_advisory_xact_lock(project)` as `update_settings` does (`projects/service.py:313-314`); compare `expected_latest_version`; refuse a body identical (`body_sha256`) to the current version (`GUIDELINE_UNCHANGED`); insert v(n+1) (n = highest version, withdrawn ones included) into `guideline_versions` and `guideline_contents`; upsert the uploader's read row (`notified_at`, `opened_at` = now); audit `guideline.upload`. Authorization: `require_project_management(..., Action.MANAGE_PROJECT_SETTINGS)`.
- **Withdraw:** same authorization and lock; compare `expected_latest_version`; refuse an unknown version (`GUIDELINE_NOT_FOUND`) or an already withdrawn one (`GUIDELINE_ALREADY_WITHDRAWN`); validate the reason (G13); delete the `guideline_contents` row, insert the `guideline_withdrawals` row; audit `guideline.withdraw`. No submission, review or read row is changed.
- **Stamp at submit:** in the submit transaction of `Repository` (the `Submission` branch at `storage/repository.py:3127-3149`) and of `TranslationReviewService.submit` (`application/translation_reviews.py:391`, insert at `477`), read the current version (G25; NULL when none is in force) and pass it into the insert. Imported submissions (`imported=True`) get NULL. A concurrent upload or withdrawal either commits before the submit's read or after; both outcomes are correct statements of "the version in force at submit".
- **Notice computation** for the task owner, editable tasks only (G27; the server excludes submitted tasks and other users' rows and computes the current version once per project for list views, the client excludes held tasks and read-only rounds): current version L (none → no notice); the user's highest version with `notified_at` or `opened_at` set, S (or none). Notice when L exists and (S is none or L > S). The notice lists the versions in (S, L], newest first, at most 5 (then "and n earlier changes"): their change notes, and "withdrawn" for withdrawn ones.
- **Removed:** `ProjectSettingsChange.guideline_url`/`guideline_version`, `validate_guideline`, error code `GUIDELINE_INCOMPLETE` and its frontend message.

## Permissions and audit

- Upload and withdraw: `MANAGE_PROJECT_SETTINGS` (leads, system admins). Read versions, record own reads: `VIEW_PROJECT` (all members, system admins). `reach` counts and `not_seen` names: leads and admins only. A user's reads are written only for themselves.
- Audit events (`auth/audit.py:42`): `guideline.upload` (target `guideline` / `{key}:v{n}`, details `version`, `kind`, `size_bytes`, `sha256`, `previous_version`; no file name and no change note, because the audit log is append-only and must not keep what a withdrawal deletes), `guideline.withdraw` (same target, details `version`, `reason`, `was_current`). Reads and notices are not audit events; they live in `guideline_reads`. `project.update` no longer lists guideline fields.

## Export

- **T1 bundles** (`exchange/jobs.py:300-330`, own-work and all-work exports, final export): `ProjectExport.guideline_ref` is replaced by `guideline_refs: dict[submission_id, str]` built from each submission's stamp (G20); `submission_to_unit` receives the submission's reference. Submissions without a stamp get `guideline_ref = None`. A withdrawn version keeps its reference.
- **Frozen snapshots** (`exchange/final_content.py:16`, `106`): snapshots store `guideline_refs` instead of the single `guideline_ref`. There are no existing snapshots (no productive data, G18), so no compatibility path for the old field is needed.
- **Final export archive:** no guideline files and no guideline list in `receipt.json` (G20); the results inside carry their `guideline_ref`. `index.csv` gains the last column `guideline_version` (empty when not recorded). README (`exchange/final_export_guide.py:200-235`) gains one paragraph explaining `guideline_ref` and stating that the guideline texts are not part of the archive and are read in Ontotator.
- **Translation review export** (`exchange/review_export.py:120`): each row gains `guideline_version`, `guideline_ref` (null when not recorded) and `guideline_withdrawn` (bool). The format stays `ontotator-translation-review/v1` because the change is additive (G26).

## Edge cases

- **Version published while a task is open:** the button and notice update on focus; a submit after that records the new version even if the person never opened it (G15). The submission label then honestly shows the version in force.
- **Draft started under v2, submitted under v3:** records v3. Only submission time counts; drafts carry no stamp.
- **Reopened task, restarted round, carry-forward or consolidation round:** each new submission records the version at its own submit; earlier submissions keep theirs.
- **Lead correction of a translation (lead follow-ups FD1):** an ordinary translation review row; stamped like any other.
- **External acceptance (lead spec D20) and imported submissions:** not submitted in Ontotator; no stamp.
- **Project with no guidelines:** no button, no notice, stamps NULL, no `guideline_ref`. The first upload produces the first-exposure notice for everyone.
- **Skipped versions:** a user last notified of v1 who opens a task after v2 and v3 sees one notice for v3 listing both change notes.
- **Member added after v3:** sees the first-exposure notice for v3 on their first editable task.
- **Read-only (submitted) task:** button and badge shown, no notice, nothing recorded until the drawer is opened (G27).
- **Same file uploaded again:** refused (`GUIDELINE_UNCHANGED`); a deliberate "restore" of an older file is allowed because it differs from the current version.
- **Wrong or confidential file published:** the lead withdraws it (G25); text, file name and change note are deleted from the database. Exports never contained the text (G20), so downloaded archives are unaffected. Copies outside Ontotator (database backups, copies people made themselves) are not reached; the withdraw dialog does not promise more.
- **Current version withdrawn:** no guideline in force; the task button disappears on the next refresh; new submissions record NULL; the next upload gets the next number (v5 after a withdrawn v4) and produces the update notice, listing "v4: withdrawn".
- **Older version withdrawn:** the current version is unaffected; submissions made under the withdrawn version show "Guidelines v2 (withdrawn)".
- **Drawer open during a withdrawal:** the next refresh replaces the text with "v3 was withdrawn by the project lead."
- **Very long Markdown or wide tables:** the drawer scrolls vertically; tables scroll horizontally inside their own container; long words wrap (`overflow-wrap: anywhere`).
- **Markdown with HTML, scripts, `javascript:` links, images:** HTML shown as literal text or dropped, unsafe links removed, images not loaded (G12). Covered by tests.
- **CRLF line endings:** stored as uploaded (after BOM removal); the renderer and `<pre>` treat them as line breaks.
- **System admin without membership:** can read, upload and withdraw; gets no notice (no tasks).
