Every state transition has an actor, UTC timestamp, reason where specified, request ID and monotonically increasing workflow revision. Existing immutable annotation/evidence hashes remain unchanged.

### New and legacy key contracts

New round-aware requests use the existing strict key model with a validated paired discriminator: `format_version` and `round_id` must both be present or both absent. Both absent fields are excluded entirely from legacy serialization, preserving six-field keys. This deliberately replaces the initial separate-model proposal without accepting permissive or unversioned extra fields:

```json
{"format_version":"ontocurator-workspace-key/v3","project_key":"p","document_id":"d2","annotator_id":"anna","mode":"independent","scope_id":"scope-hash","target_set_id":"targets-hash","round_id":"r2"}
```

Persist this key as `wk3|` followed by percent-encoded components in the displayed order, excluding format_version and including round_id. All legacy `_key_str` bytes and `_workspace_aliases` behavior remain unchanged **inside the legacy decoder only**. A v3 key has exactly one storage key and no old-key aliases. The server returns the authoritative key; clients cannot manufacture a round by posting an arbitrary ID.

New rounds emit `ontocurator-submission/v3`, containing that origin key, frozen input manifest hash, carry-forward resolutions and existing snapshots/evidence/reanchor material. Model validation rejects a v3 key without the v3 submission format/digest and rejects round metadata on legacy origins. Legacy v2 serialization excludes absent new fields, including empty resolutions. Draft/search-event/receipt containing formats remain unchanged and reuse the strict nested key decoder; stored old event/receipt/state payloads are never rewritten. This bounded nested-format adapter replaces a new envelope family and central registry: `_decode_key_str`, strict `WorkspaceKey` and `Submission` validators are the shared boundaries.

The repository's existing in-memory `PackageManifest`/`ValidatedPackage` contract gains work-package/v3; there is no existing workspace ZIP writer to extend. V3 adds `workflow_history` keyed by round ID and explicit `proposal_annotation_refs`/`proposal_evidence_refs`. History contains immutable round view, frozen inputs and bound submission IDs; package snapshots include exact historical source/target/evidence closure. Explicit proposal inventories prevent human snapshots becoming global proposals on import. Validation checks each input against its owning immutable submission and package snapshots. Imported history remains in the project's original manifest and reads as inactive historical data; it does not restore users, assignments, live holds or final selections. New local authority is required for new work. Legacy v1/v2 packages exclude every new field and retain their old decoder. V3 histories cannot be represented as v1/v2 by the validator. This replaces the initial nonexistent `workflow.json` archive design; report events/holds and cross-project live activation are deliberately not claimed as resumable package state. T1 is a separate scientific export.

Migration procedure:

1. Migration 0010 adds defaults/policy revision; 0011 adds round definitions/state/bindings/inputs/receipts/source resolutions and draft input resolutions; 0012 adds final records; 0013 adds reports/holds and assignment hold projection. Make no UPDATE to immutable submission, snapshot, receipt or search-event payloads.
2. Bind legacy annotation work lazily on explicit authorized open, not by eager timestamp inference. Preserve the selected legacy key and established equivalent independent aliases, bind its exact historical submissions, and create one ordinary sidecar round. Unopened legacy history remains readable through the legacy adapter.
3. Preserve existing explicit review-target selection when several legacy target sets exist. An authoritative assignment `last_submission_id` must match the selected origin; otherwise reject `AMBIGUOUS_SUBMISSION_ORIGIN`. Never merge independent/assisted/imported origins or infer one from timestamps. Once active, another legacy key cannot become writable implicitly. There is no general-purpose historical activation endpoint in this bounded change.
4. Continue a legacy active round using its unchanged v2 origin and revision chain. A new restart/carry-forward/consolidation gets v3. Legacy key writes are accepted only while their bound round is active and editable. Historical reads and receipt replay remain possible under current read authority.
5. Profile/scope or mode changes never silently rebind a round. An assignment open returns its existing active round; a mode toggle cannot create a second editable attempt. New annotation rounds currently derive independent/review mode from the existing task. Legacy assisted history remains readable; arbitrary new mode-switch rounds are outside this bounded API.

Translation reviews retain their existing assignment-keyed mutable draft and save/submit envelope. A deliberate accepted correction or report restart creates a round with `mode=null`, `workspace_key=null`; its submission pointer uses the immutable existing `tr-<review_id>`, not the annotation-submission FK binding table. Draft revisions remain monotonic across restarts, so old requests cannot target the replacement draft. A report restart archives abandoned text/form/revision in its immutable report event and resets to exact target text plus empty form. Existing immutable review records remain intact. This explicit adapter avoids replacing the established translation-review schema solely to resemble annotation work.

`latest_submissions` continues selecting by full immutable origin and draft revision. Its caller filters active/non-abandoned local bindings for current-work projections; history endpoints do not filter them. A submitted old round must not make a new empty round appear completed. FinalSelection deliberately may still point to a superseded/abandoned round, with warning. Task list counts distinguish held from underlying submitted/in-progress status.

All endpoints below live under `/api/v1`. Round transitions use `request_id`/`expected_workflow_revision`; report actions use `request_id`/`expected_revision` of the report. Annotation writes keep `MutationEnvelope` (request ID, exact key, expected draft revision); translation writes keep their existing expected draft revision. Exact active-round checks happen transactionally even when the public envelope does not duplicate workflow revision. Invalid authorization is not downgraded to a warning.

### State transitions

| Before | Command | After |
| --- | --- | --- |
| editable, unheld | save / submit | Same round; revision increments / round submitted and exact assignment last submission updated atomically. |
| editable or submitted | report/extend hold | Same content and underlying status, hold active. New writes blocked. |
| held editable | release last hold | Same preserved editable draft. |
| held submitted | release last hold | Same submitted read-only result; lead reopen is separate. |
| held or unheld | agreed clean restart | Old round abandoned, new empty editable round; release only this report's hold. If another hold remains, reject atomically without creating a round. |
| old task on corrected document | continue on correction | Create target-document assignment/round with explicit frozen source. Preserve source task/history/state; its immutable submission remains an input, not a mutable predecessor on the new assignment. Holds release only by explicit command. |
| submitted, unheld | lead reopen | Same round editable, same frozen inputs, new subsequent submission possible. |
| superseded/abandoned | any new write | Reject `ROUND_NOT_ACTIVE`; historical reads/previous receipts remain readable. |

Lock order must be shared by annotation, translation, assignment, hold/restart and export paths: existing import mutex when needed → members advisory lock → project advisory lock → sorted authority/user locks → sorted assignment row locks → round state → draft advisory/row locks. This moves assignment validation before draft mutation consistently; do not add a reversed lock order to `before_operation`. Administrative transitions, source-producing operations and final snapshot creation use project EX; ordinary work uses project SH. Existing repository structural import locks must cover every producer.

Under assignment/round locks, recheck current membership, owner, active round, hold state, expected workflow revision and existing translation gate. A save that commits before hold is preserved; once hold commits, a later save or submit must fail without any content write. Apply these guards to annotation editing, decisions, reanchor completion, document/layer checks, submission, search-event writes that mutate workspace history, reopen, translation save and translation submit. Read-only searches remain possible.

Receipt replay returns the previously committed immutable result even if the round is now held/superseded, after current read authorization. Existing mutation transport exposes replay semantics; do not mutate stored receipt bodies or infer editability from historical content. Current assignment/round GET/open supplies editability. Clients only install responses matching their current assignment/round/session generation. An old submit replay cannot update a new round's task status.

## 4. Frozen human inputs, carry-forward and consolidation

Carry-forward is deliberate at target-task opening, not a background copy triggered by viewing a version. The server offers the owner's exact authoritative latest submitted ID, then rechecks active submitted round state under project/assignment locks before freezing it. Legacy sources use exact assignment last-submission identity, never timestamp guesses. Unsaved/unsubmitted work is not silently converted into a submission. If no eligible submission exists, offer an ordinary empty target round. A hold blocks target task mutation but does not revoke read access to an immutable submitted source; the source hold/report remains an independent visible cause.

Input and target must share project, case, language and exact correction ancestry; source may be several versions behind. Validate each immutable ancestry edge and map directly from frozen source text/hash to target text/hash; the inventory retains the exact traversable chain. Do not sequentially remap an already rounded/changed coordinate. Translation roots in the same language are independent runs and are not correction ancestors. Cross-language transfer remains unsupported.

Preserve source clinical values, default markers, annotation notes and evidence. Allocate new target annotation/evidence IDs for carry-forward; derive provenance from the exact input identity. All carried annotations, including unchanged anchors and spanless findings, require explicit review on the target text. Review consists of associate/recheck evidence, inspect/confirm values, then complete against the exact persisted snapshot. Unchanged text coordinates do not auto-confirm values. Ambiguous/missing anchors remain pending until explicitly reanchored, converted to allowed spanless with reason, or dismissed with reason. Dismissed input stays in history. No suggestions or checked-layer state from the abandoned workspace are seeded by clean restart.

Visibility uses `workspace_input_snapshots`, `get_round_input_inventory` and central `may_read_human_submission`/`may_read_snapshot` predicates. Exact offered source documents are added to task-authorized readable documents. All open/adopt/decide/reanchor/submit and raw snapshot reads enforce these restrictions; export resolves explicit immutable closure. Anna sees only Anna's inputs; Ben sees only Ben's. Lead administration and explicitly offered consolidation inputs grant no global promotion of human snapshots into proposal inventory.

Consolidation inputs must be explicit frozen submissions on the identical internal document ID and text hash, with compatible pinned layers/profile. Equal text strings on different versions are insufficient. Cross-version inputs require explicit prior carry-forward and submission. Require at least two distinct input submissions; empty submissions are valid inputs. Input contributor identity stays attached even when annotations are identical. Reviewer eligibility uses existing review task/adjudicator role and `adjudicator_not_annotator` policy; extend the conflict check to actual selected contributors when that policy is true. When false, do not introduce a blanket contributor exclusion.

Each frozen input binds source submission plus original AnnotationRef to a distinct alias snapshot `input-<input_id>`. ReviewDecision keeps its existing target AnnotationRef shape against that alias. Internal provenance `round-input:<input_id>` resolves only through the exact frozen manifest; raw original ID/hash never identifies an owner. Existing confirmed/changed/rejected/uncertain semantics remain, with an explicit uncertain reason. A deliberate merge records every source input ID and one fresh output, while separate retained findings stay separate. Ordinary proposal review and human consolidation remain distinct round kinds.

An immutable uncertain source remains a source snapshot plus a reviewer decision, not a copied clinically edited annotation. Output projection can allocate a unique output ID while preserving clinical values, source actor/method, evidence and source URI. Export receipt records `(output set/id → source input/id/version)` so ID disambiguation is explicit. For confirmed/changed/merged outputs, actor is reviewer and method adopted/edited/merged; notes from the source stay source notes, and reviewer reasons remain separately attributed in the receipt or T1 review_resolution where supported.

## 5. Source-change obligations

Derive obligations from immutable variant inventory rather than trusting one producer to emit them. For each translation root, resolve its exact historical source with `resolve_translation_lineage`; enumerate every later correction edge on that source's linear chain. An obligation cause hashes `(project, translation-root ID, exact subject translation version ID/hash, old source ID/hash, new source ID/hash)`. The subject is the translation correction-chain leaf being reviewed. A no-change acknowledgement certifies that exact subject text only: later changed translation text requires a fresh cause for every applicable source edge, including one acknowledged on its predecessor. When the explicit source-resolution transaction creates accepted_corrected text, it resolves both old and new child causes for that same edge. Ordinary correction alone never implies it reviewed updated-source differences. This clarifies and replaces the earlier ambiguous phrase “inherits unresolved causes”.

This covers interactive correction, uploaded T1 variants, package import and CLI inventory additions. A new translation rooted directly in the newer source has no obligation for changes before that source. Independent source/translation roots do not create obligations against one another. Malformed/missing ancestry fails integrity validation; it is not “no obligations”.

The review screen shows both “Originally translated from” and “Review against updated source” with exact versions/texts. No-change resolution records accepted_unchanged review plus source relationship in `review_obligation_resolutions`, with no new text version. Corrected resolution records accepted_corrected review, new translation version, source cause and re-review requirement for annotations. Neither path rewrites `derived_from` of the old translation or the predecessor link of its correction.

One command resolves one exact cause. A reviewer may explicitly submit a displayed list of causes in one transaction, but clearing the oldest or newest cause alone does not clear others. A later source correction always creates a new cause regardless of previous confirmation. Repeated correction of accepted translation v2→v3 uses the deliberate assignment endpoint, retains qualification/language/role/stale-parent checks and preserves prior accepted review records and pinned selections.

## 6. Defaults, strict confirmation and search preferences

Task 8 adds `creation_defaults[layer_id][type_id][axis_id] = value` and a monotonic `annotation_policy_revision` to project settings. Keep `require_chosen_axes`: false means warnings require conscious acknowledgement; true means mandatory confirmation. Do not add a second policy flag that can disagree with it. Existing true values remain true; new projects default false. Defaults must be legal, visible values on the named profile type. Applying defaults is creation-only; carry-forward/import/existing annotations never receive new defaults retroactively.

Creation command gains optional `chosen_axis_ids`. Modern clients always send the list, including an empty list when nothing was consciously chosen. An omitted value uses the configured default and is marked defaulted; explicit null stays unset; with explicit metadata a supplied value counts as chosen only when named in the list. A named axis must have a valid nonempty supplied value. For compatibility, legacy commands omitting the metadata preserve supplied non-preset values as chosen, while supplied values matching a configured preset remain defaulted. This adapter retains existing explicit-creation semantics without treating configured preset prefills as proof of confirmation. Existing update confirmation semantics remain unchanged.

Warning acknowledgement contains exact draft key/revision, policy revision and canonical warning digest. Submission validates all three and records the acknowledgement in the audit/event path or immutable submission-context sidecar. It does not alter existing submission/v2 content. Any intervening edit or relevant settings change requires another acknowledgement. Hidden values, malformed evidence, invalid terms and other integrity failures remain errors.

Strict checking still covers every axis defined on the annotation type, including axes with no configured preset. Missing values cannot be confirmed; users must choose a permitted value, including an explicit profile-defined unknown/unspecified value when available. Optional profile axes may remain absent under warning mode, but strict mode continues the existing all-axis rule. This is deliberately documented because “no preset” does not mean “not required”.

For immutable Unresolved inputs, explicitly expose the strict-policy conflict. An unresolved source with defaulted or absent axes cannot meet require_chosen_axes; submission remains blocked with exact source/axis violations. The UI explains that retaining Unresolved preserves immutable source values and that the lead must consider the project's warning policy if that result should be submitted unchanged. The reviewer may independently choose a clinically justified edit, but the UI must never suggest or perform replacement merely to clear this restriction. No automatic policy downgrade or reviewer-attestation subsystem is introduced. Warning mode allows explicit acknowledgement with source default markers and Unresolved preserved; malformed/missing mandatory clinical values still fail ordinary completion validation. T1 continues expressing the source basis truthfully. This selects the plan's explicit-rule-conflict alternative.

Task 9 stores one durable user-level `multilingual_search` object: `{enabled:true, preferred_languages:[], automatic_document_language:true}`. Empty preferred list means “no extra preferred languages”, not “all installed”. First use searches English plus the current document language if actually loaded; canonical English/ID search is always available. `enabled:false` disables translations and automation without deleting saved choices. Temporary editor overrides never persist unless the user chooses Save preferences.

Migration: if the authenticated user's existing pseudonym has `search_languages_by_annotator`, preserve that exact list, retain enabled:true with the exact preferred list (including []), and set automatic_document_language false to preserve an explicit prior restriction. A null object means use the legacy adapter. If no matching list exists, use the first-use defaults; do not merge another annotator's list or let last_annotator_id choose it. Preserve old stored lists for compatibility/history but the new object takes precedence and must not be discarded by `_from_stored`. Unavailable preferred languages remain saved and are shown unavailable; effective search is the intersection with loaded compatible translations. Use the existing row-lock merge behavior for section updates.

## 7. Warning projection and selection scope

Expected final coverage is each distinct `(case_id, language)` actually represented in the project's authorized document inventory, including imported/native/translation variants regardless of whether assigned or accepted. A case/language is one selection slot across its independent roots. Do not invent missing target languages from user preferences or language skills. Empty projects have no slots; export is still refused as empty.

`GET /projects/{key}/workflow-warnings` and `POST /projects/{key}/exports/final/preflight` use one pure server projection over the same authorized inventory/round/report/selection/obligation state. Each warning has `id`, `code`, `cause_revision`, case/language, relevant exact task/round/document/selection IDs, plain reason and authorized destination. Its identity hashes code plus immutable cause references; revision changes when its actionable state changes. Sorting is stable. The projection returns a canonical digest; it is not separately stored dashboard state.

| Warning | Exact scope and resolution |
| --- | --- |
| `MISSING_FINAL_SELECTION` | Every covered case/language without an explicit selection. Preflight lists omission. Resolve by selection, never latest-result substitution. |
| `OPEN_PROBLEM_REPORT` / `TASK_ON_HOLD` | Open reports/holds on any relevant task in the covered language; dashboard and preflight both show them even if that task is not selected. Redact reporter content from people lacking lead authority. Close/release exact cause. |
| `SELECTED_ROUND_ABANDONED` / `SELECTED_ROUND_SUPERSEDED` | Selected submission's own round changed state. Selection stays pinned; lead replace or consciously keep it. |
| `SELECTED_RESULT_REVISED` | A higher draft revision was submitted in the selected result's same logical round/origin after its selection baseline. An unrelated person's new submission does not trigger it. Draft autosaves alone do not produce result revisions. |
| `SELECTED_TEXT_CORRECTED` | A new correction descendant on the selected document's own chain appeared after the selection baseline. Other translation roots/siblings do not trigger it. |
| `SOURCE_UPDATE_UNREVIEWED` | Exact pending obligations on the selected translation chain; also visible as project issues when that chain has active work. Independent unrelated chains do not invalidate a selection. |
| `ROUND_REVIEW_PENDING` | Active carry-forward/consolidation or translation review on the selected chain has unresolved required work. Resolve that work, or retain the explicitly warned selection. |

Reaffirming the same final pair can acknowledge finite “result revised/text corrected/round superseded” causes in a new selection event, preventing permanent stale-selection warnings. It cannot mark reports, holds or source obligations resolved. Missing selection, invalid ancestry, missing immutable inputs and authorization are never erased by a warning acknowledgement. Final export acknowledgement applies to one snapshot only; future new causes invalidate the digest. Open independent work is not automatically an error or a consensus demand.

## 8. Final-export transaction and T1 examples

Final preflight response:

```json
{"state_digest":"sha256-of-canonical-state","selection_revisions":[{"case_id":"GSC17","language":"en","revision":3}],"warnings":[{"id":"w1","code":"MISSING_FINAL_SELECTION","cause_revision":1,"case_id":"GSC17","language":"de"}],"omissions":[{"case_id":"GSC17","language":"de"}]}
```

`POST /projects/{key}/exports/final` accepts `{request_id, state_digest, acknowledged_warnings:[{id,cause_revision}], accepted_omissions:[{case_id,language}]}` (the digest includes every exact selection and its revision; no redundant independent revision list). Under members/project locks and fresh export-all authority, recompute the complete projection, verify exact set equality including absence of new warnings/coverage, resolve immutable inputs and create snapshot and job **in the same database transaction**. Stale state returns 409 `REVISION_CONFLICT` with `details.reason=EXPORT_PREFLIGHT_STALE` plus `details.preflight`; no job is created. No blanket `continue:true` can waive staleness or integrity.

Reject `EXPORT_EMPTY` when zero selected results would be exported, including an entirely missing-selection project. One valid empty annotation submission is a legitimate selected result and does not count as zero results. Partial export is allowed only with every missing-language omission explicitly accepted. Warned selected results remain included.

Job kind `final_t1_export` has exactly `{project, snapshot_id, snapshot_sha256}`. Worker verifies job/project/requester/snapshot identity and current membership/account/export authority, then uses frozen IDs/hashes/pins only. It must not call live latest-selection or latest-submission queries to choose content. Later selections, warning resolutions and source updates do not alter the snapshot. Deleted/unavailable inputs, changed immutable hashes or revoked authority fail the job. Download authorization remains current as in existing job routes. Audit records job ID, snapshot hash, artifact hash, selected pairs, omissions and acknowledged warning identities.

The final artifact is an outer ZIP with `selected.t1.zip`, optional `provenance.t1.zip`, `source-texts.jsonl` and `receipt.json`. Each inner ZIP is an unmodified standard ontospan bundle. The receipt uses `format: ontocurator-final-export/v1`, hashes every payload file, and distinguishes selected units from provenance-only units. Source-text records contain exact Document/Variant identities and text hashes for ancestry/obligation closure where no annotation set exists; they never masquerade as empty selected annotation results. Existing all-individual export keeps its plain T1 artifact and explicit route/kind; CLI stays that mode until a final client implements this exact preflight protocol.

For each selected or recursively referenced human submission, set ID is `submission-<submission_id>`. Each provenance bundle has deterministic ID `provenance-<snapshot_id>` and the selected bundle `selected-<snapshot_id>`. Use ontospan.annotation_ref for encoding; never append content hashes to a URN by hand. The inventory maps `(owner submission/set, annotation ID, version)` to the exact output bundle/set/id; it resolves known internal refs before attempting external-URN parsing. Reuse Task 1's mapper boundary and extend its inventory, not its parser heuristics.

Include frozen input units outside final selection as provenance-only closure, plus exact evidence/text for all references. Detect cycles and missing records as errors. Preserve externally qualified historical URNs and their known original identities; package their locally available exact source units, recording origin-to-packaged aliases in the receipt. An external ref absent from the local frozen inventory is explicitly listed as external/unresolved provenance in the receipt; an input declared as a frozen local human source must never be treated as such an escape hatch. No export worker may broaden closure from “all results on this document”. Contributor names/ORCIDs remain consent-controlled; pseudonymous actor IDs preserve attribution.

## Implementation checkpoint: final-result wire and artifact details

Final selection uses `PUT /projects/{key}/final-selections` with exact `document_id`, `submission_id`, `expected_revision`, and optional `acknowledged_cause_ids`. The server derives the case/language slot from the immutable document rather than trusting a second caller-supplied slot identity. Reaffirming the same exact pair retains previously acknowledged specific causes; replacing it cannot acknowledge future causes. The monotonic revision is returned.

Final artifacts contain `selected.t1.zip`, optional `provenance.t1.zip`, `source-texts.jsonl`, and `receipt.json`. Each T1 ZIP carries its own ontospan manifest and JSONL files; source bundle IDs are `provenance-<snapshot_id>` and selected bundle IDs are `selected-<snapshot_id>`. Human source set IDs are `submission-<submission_id>`. A source already explicitly selected is referenced in the selected bundle and not duplicated as provenance-only. The receipt identifies exact selections, source input aliases/original IDs, separately attributed review decisions/notes, acknowledged warnings, omissions and artifact hashes. Both contained bundles are independently validated by ontospan. Consolidation sets are `stage_result`/`consolidation`; carry-forward stays `individual`/`carry_forward`.

Research export retains latest-per-person/task semantics, expands only the exact transitive human source closure needed to interpret those results, and labels any historical source-only submission IDs in job metadata. It never invokes final-selection semantics. Private input aliases and the qualified internal `round-input:<input_id>` token resolve through the same frozen exact-input inventory; arbitrary colon-bearing or hash-like references are not guessed.

Final source-review receipt: `content.source_reviews` freezes each relevant immutable obligation resolution together with its immutable translation review record. The archive exposes these as `receipt.json.source_reviews`; exact old/new reviewed source texts and their ancestry are included in `source-texts.jsonl`. Internal user IDs are excluded from the review record; the recorded reviewer pseudonym and review metadata remain. Unrelated unselected review chains are not added merely because their records exist.
