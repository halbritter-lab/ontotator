Spec: `docs/superpowers/specs/2026-10-14-t2-server-foundation-design.md` (binding). Roadmap and decisions E1–E12: `docs/superpowers/specs/2026-10-14-roadmap-web-service-analysis.md`. Format: T2a gives complete code for every step. At the user's request, T2b–T2e use a lean format: files, interfaces, table definitions, named test cases with their assertions, acceptance criteria and exact verification commands. Code appears only where it defines a contract (grants and triggers, CSRF and session handling, the policy table, the job claim, the image build). Implementing agents write the rest test-first.

Branches: each plan works in its own worktree and branch (`feat/t2a-postgres-storage`, `feat/t2b-accounts-sessions`, `feat/t2c-projects-authorization`, `feat/t2d-ontologies-exchange`, `feat/t2e-docker-operations`). Each branch is created from the previous plan's branch once that plan is reviewed. Nothing is pushed without the user's confirmation.

## Constraints that apply to every plan

- **No GitHub Actions.** The user has no CI minutes. No plan adds or relies on a workflow job, and `.github/workflows/ci.yml` stays as it is. All verification is local. `scripts/check.sh` (created in T2a) runs the complete local gate.
  - The existing workflow becomes stale: it would need a PostgreSQL service to pass. That is accepted and recorded here.
- **PostgreSQL in tests (P8):** tests use PostgreSQL through testcontainers. Docker Desktop must be running. `ONTOTATOR_TEST_PG_URL` can point to an existing throwaway server instead.
- **Commits:** conventional messages, no AI attribution lines, no `Co-Authored-By` trailers.
- **Files are English.**
- **Windows:** commands are written for Git Bash on Windows; they also work on Linux and macOS.

## Resolved decisions (user, 2026-10-14)

- **R1, login identifier:** users log in with a **username assigned by the administrator**. E-mail is an optional contact field. It can later become a transport for setup and reset codes (D2). This refines E2 ("email and password").
- **R2, no CI:** see above. P8's "service container in CI" is replaced by local testcontainers runs. Access to the private `ontospan` repository is therefore needed only for local `uv sync` and for the Docker build.

## Technical decisions made in the plans (with rationale)

| # | Decision | Rationale |
|---|---|---|
| D-a | Typed declarative mappings (`Mapped[...]`) for every table; the repository runs Core-style `select`/`insert` against them on a `Connection`. No ORM unit of work. | Satisfies P2's typed mappings. Snapshots stay plain JSON payloads, and the transaction behaviour of the old repository is easy to preserve. |
| D-b | Ambient transactions: `Database.transaction()` joins the transaction already open in the current context. | Editing operations call the repository from inside `run_mutation`. With SQLite they shared one connection; this keeps them atomic. |
| D-c | Two database roles: `ontotator_owner` owns the schema and runs migrations, and `ontotator_app` is the runtime role. The runtime role may only `SELECT`/`INSERT` on append-only tables, and triggers reject `UPDATE`, `DELETE` and `TRUNCATE` there. | D6 requires that even an application bug cannot rewrite history. Limin's single role that owns its schema could change everything. |
| D-d | Migrations run as a one-shot `migrate` service with the owner credentials, before the app starts. They are forward-only and serialised by an advisory lock. The app never holds owner credentials. | Keeps D1's "never superuser" and D-c's privilege separation. `/readyz` reports pending migrations. |
| D-e | `WorkspaceKey.package_id` keeps its name in T2 and carries the **project key**. | Renaming it touches the domain, about 40 test files, the OpenAPI contract and the frontend. That rename is mechanical and is deferred to T3, which rewrites project selection anyway. |
| D-f | The in-memory `ValidatedPackage` remains the internal seed structure for tests and the browser fixture server. The v2 ZIP reader/writer, its endpoints and buttons are removed in T2d. | P1 replaces the v2 *format*. The in-memory model is the existing test fixture mechanism for about 500 tests, so keeping it avoids rewriting them. |
| D-g | One test database per test, cloned from a migrated template database (`CREATE DATABASE … TEMPLATE`). | Full isolation, including for tests with several connections and threads. It costs about 50 ms per test. |
| D-h | Session cookie `ontotator_session` (HttpOnly, SameSite=Lax, Secure on HTTPS). The token is stored only as SHA-256. Synchronizer CSRF token in the `X-CSRF-Token` header. Requests without a session (login, code redemption) are protected by an Origin / `Sec-Fetch-Site` check (Limin pattern). | P3. Phentrieve's double-submit cookie is weaker and only covers two endpoints. |
| D-i | Argon2id with the OWASP parameters m=19456 KiB, t=2, p=1 (Limin `ARGON2ID_POLICY`). The bootstrap hash must meet at least this policy. | P4. Phentrieve itself uses bcrypt, so its parameters cannot be reused. |
| D-j | Login throttling is per account and per client address, recorded in `login_attempts`. Unknown users are verified against a dummy hash. Every failure gives the same 401 `LOGIN_FAILED`. | Fixes the Phentrieve weaknesses found during planning: no window, a 429 that reveals the account, and timing differences. |
| D-k | The authenticated actor travels in a `ContextVar` set by the HTTP middleware. The repository reads it when it writes `edit_events`. | FastAPI runs sync endpoints in a thread pool; only context set before the endpoint call reaches it. |
| D-l | Jobs are claimed with `FOR UPDATE SKIP LOCKED` by a worker thread in each app process. CLI commands enqueue a job and run it inline (`--wait`, the default), so the CLI works while the server is stopped. | P6 without Redis. |
| D-m | Ontology bytes and translation files live in `/data/blobs/<aa>/<sha256>`, with metadata in `stored_files` and `ontology_files`. | D3. |
| D-n | `ontospan` is a Git dependency pinned to the merge commit `263368b` on `main` (PR #1, merged with a merge commit). The Docker build gets read access through a BuildKit secret (`--secret id=github_token`). | T1 F12 and the T1 plan's note T1-27. With no CI, only the image build needs the token. |

## Resolved user-flow and domain questions (user and coordinator, 2026-10-14)

The plans first carried these as open questions, each with a provisional default. They are now decided. The plans mark the affected code with `Resolved Qn`.

| # | Question | Decision |
|---|---|---|
| Q1 | Scope of the pseudonym (T1 F10) | One stable pseudonym per user (`ann-0001`, …), assigned at creation and used in every project |
| Q2 | Who may use which working mode | `independent` and `assisted` need the annotator role; `review` needs the adjudicator role. A lead or a system admin needs the corresponding role too. |
| Q3 | What a reviewer sees in review mode | **Changed from the desktop behaviour:** a reviewer sees only what is assigned to them, because anything else could bias them. In T2 there are no assignments yet, so review mode shows **only the document's proposal sets**, never other members' submissions or drafts. Other members' work becomes visible only through T4 workflow assignments (E8). |
| Q4 | What a system admin sees | Every project list, document and export; annotating needs a membership |
| Q5 | Who exports results and the edit log | Project lead and system admin |
| Q6 | Session lifetime | 12 h idle, 14 days absolute (technical; coordinator) |
| Q7 | Password rules | 12 to 256 characters, not the username, no composition rules (technical; coordinator) |
| Q8 | Login lockout | 5 failures per account or 30 per address within 15 min lock for the rest of the window; the message never says "locked" (technical; coordinator) |
| Q9 | Setup and reset flow | Code form on the login page ("I have a setup or reset code"); the user is logged in afterwards |
| Q10 | What the UI shows about the user | Display name plus pseudonym |
| Q11 | T1 import of unsupported content (e.g. modifiers) | Refuse the whole import, listing every affected annotation |
| Q12 | What the T1 export contains | Per document and annotator, the latest submission of each mode as an `individual` set (`stage` = mode, `blind: true` only for `independent`). Consistent with Q3, a review submission exports only the reviewer's own resulting annotations: adopted proposals (`adopted`), changed ones (`edited`) and new ones (`manual`). Rejected and uncertain decisions are left out and counted. |
| Q13 | Axis `basis` in the T1 export | A set value is `chosen`; an empty value in an `hpo-phenotype` layer becomes the profile default with `defaulted`; in `generic` layers it is left out (technical; coordinator) |
| Q14 | Edit-log export | Pseudonyms, no session ids, exact UTC timestamps to the second (technical; coordinator) |

## Deviations from the spec

- **P8:** no CI service container (R2); local testcontainers only.
- **D1, migrations:** a separate one-shot `migrate` service with owner credentials instead of migrations at app start (D-c, D-d). Limin migrates at server start because its runtime role owns the schema; that is incompatible with D6's grants.
- **P1 and E6:** `ValidatedPackage` survives as an internal seed structure (D-f). `WorkspaceKey.package_id` keeps its name (D-e).
- **Data model:**
  - `document_order` becomes a `position` column of `documents`.
  - `review_decisions` holds the decisions of a draft. Submitted decisions stay inside the immutable submission payload.
  - `search_events` and `mutation_receipts` are kept from v4.
  - New tables: `project_resources`, `project_search_conditions` and `stored_files` (search-condition pins and D3 files), `login_attempts`, `user_preferences` (replaces the per-workspace preferences file) and `instance_state`.
- **No API or UI for user administration in T2:** D5 already places it in the CLI. Users change their password only through a reset code from an admin until T3.
- **The desktop launcher, provisioning folder, legacy settings import, distribution presets and the PyInstaller build are removed** (P1, E1). T2a removes the backend parts and T2b the remaining frontend parts.

## Risks

- **Docker is required for every backend test run.** Without a running Docker Desktop the suite stops at the first database fixture with a clear message.
- **Order-dependent tests:** SQLite returned some rows in index or insertion order without `ORDER BY`. The port adds explicit orderings (T2a Task 6). A test that relied on another implicit order fails visibly and is fixed in that task.
- **Dashboard listing cost:** document status is computed per document and annotator, as in v4. T2e measures it (budget: p95 < 500 ms for 1 000 documents). If it is over budget, a batched status query is a contained follow-up.
- **Frontend size:** T2b and T2c edit `App.tsx` (about 1 150 lines) with exact replacements. A parallel frontend change on `main` would conflict.
