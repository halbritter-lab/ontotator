**Split rule:** a subproject is split only where one plan would exceed about 1,000 lines. T3 (about 1,050 lines in total) is therefore two plans, T5 is one plan, and T4 (about 1,850 lines) is two. Within a merged plan, Part 1 is the backend and Part 2 the user interface. The repository is green after every task.

Format: lean, as T2b–T2e. Per task: files, interfaces, tables, named test cases with their assertions, acceptance criteria and exact local commands. Code appears only where it defines a contract. Implementing agents write the code test-first.

Worktrees: `.worktrees/<branch without feat/>`, created from the previous plan's branch. Nothing is pushed without the user's confirmation.

## Constraints that apply to every plan

- Everything from the T2 index: no GitHub Actions (R2), PostgreSQL through testcontainers (Docker Desktop must run), conventional commits without AI attribution, English files, Git Bash commands.
- **Ontocurator stays generic** (user decision). No benchmark- or Phentrieve-specific code, names, formats or defaults. Consumer adapters live with their owners (T7 appendix).
- **Commit rule per task:** `uv run ruff check --fix src tests && uv run ruff format src tests && uv run mypy src`, then one commit.
- **Contract regeneration** after any API change: `uv run python scripts/export_openapi.py && npm --prefix frontend run api:generate`.
- **Embedded assets** after any frontend change that a plan ends with: `npm --prefix frontend run build`, then replace `src/ontocurator/web/` with `frontend/dist/`.
- **Full gate** at the end of every plan: `scripts/check.sh`, expected `All local checks passed.`

## Technical decisions (with rationale)

| # | Decision | Rationale |
|---|---|---|
| D-o | A document variant is a `documents` row. `documents.document_id` becomes the internal variant id; `external_id` keeps the T1 `document_id`. The first variant of an external id uses it unchanged; any further variant gets `"{external_id}~{language}~v{version}"`. | Drafts, submissions, edit events, assignments and proposals all key on `(project, document_id)`. Keying variants the same way avoids rekeying all of them. Existing documents are already "a case with one native variant". |
| D-p | A small hash router (`frontend/src/app/router.ts`, about 60 lines) instead of a routing library. | Fewer than 15 routes, no server routing needed for the embedded SPA, no new dependency before the T6 UI overhaul. |
| D-q | `WorkspaceMode` stays as an internal draft kind (`independent` = no inherited targets, `review` = inherited targets with checklist, plus `adjudicate` in T4b). The client no longer chooses a mode: it opens a workspace by assignment id and the server derives the key. A stage draft carries its stage in `target_set_id = "stage:{document_stage_id}"`, because `scope_id` must stay the `build_scope` hash. T4a converts T3's `review` task into an annotate stage with proposals as input. | Tasks are the user vocabulary (W2, W4). Renaming the mode values would touch about 50 test files without changing behaviour. |
| D-r | Upload preview and commit share one pure `plan_import(units, project_state) -> ImportPlan`. The commit re-plans in its transaction and refuses with `UPLOAD_STALE` if the plan hash changed. | One code path for the CLI, the preview and the commit, and no time-of-check/time-of-use gap. |
| D-s | The distribution proposal is greedy least-loaded with a tie-break from `random.Random(seed)`. Load is the count of active, not yet submitted assignments in the project. | Deterministic and reproducible from the recorded seed (A2), easy to test, and balanced to within one document when everyone reads every language. |
| D-t | When a stage task is released, its result is materialised as new snapshots authored by the releasing user (`adopted`, `edited`, `manual`, `merged`). `source_refs` hold the direct parents plus the parents' imported origins (O3). | Later stages and releases need concrete annotations, and O3 then holds by construction without walking the graph. |
| D-u | Imported sets are kept as delivered in `proposal_sets.payload`. Releases re-emit `tool_output` sets from it. | Keeps the producer's ids, `basis`, notes and unknown fields exactly (O1, I3, I5), although Ontocurator's snapshots do not store all of them. |
| D-v | A translation review draft is autosaved text in `translation_review_drafts`. Only the submitted review is an immutable record (audited). Keystroke history is not kept. | The record carries the proposed text and its hash, which is what review provenance needs. D6's edit log covers annotation commands. |
| D-w | Re-anchoring diffs code points with `difflib.SequenceMatcher(None, old, new, autojunk=False)`. A segment transfers only if it lies inside one `equal` block. | Standard library, exact, and fast enough for texts of a few thousand characters; it implements V2's "unchanged regions only". |
| D-x | Adjudication groups are computed, not stored. Pairwise `ontospan.match_annotations` results are joined with union-find. A group id is the canonical hash of its member references. | Deterministic from the immutable inputs, so nothing can drift. It uses the one matcher (E7, T1 F11). |
| D-y | Comments are their own append-only log (`comments`, `comment_thread_events`). The edit-log export appends them as `kind: "comment"` lines. | W8 requires immutability and inclusion in the edit-log export; `edit_events` rows belong to drafts, and comments do not. |
| D-z | The translation review export is a generic JSONL record (`ontocurator-translation-review/v1`) with English codes. The mapping to any consumer's own record format lives in that consumer's repository. | User decision U1. The internal codes already follow the benchmark's scheme one to one (T5 V1), so the consumer mapping is a lookup table. |
| D-aa | ontospan format 1.1 (`case_id`, `variant`, `translation` on the document; the optional manifest `release` block, I7) is built in the ontospan repository as T5 Task 1. Ontocurator re-pins to the new merge commit. | T5 V4 and T7 I7 ship together as 1.1. Nothing in T3 needs 1.1. |
| D-ab | The live diff of the translation review screen uses the `diff` package (jsdiff, BSD-3-Clause, no dependencies). | A hand-written word diff would need its own Myers implementation and tests. `THIRD_PARTY_NOTICES.md` is regenerated. |

## Deviations from the specs

- **T5 V1 export:** generic JSONL records with English codes (D-z), not records in the benchmark's own format. The mapping belongs in the benchmark (U1).
- **T5 V5 provenance:** translation draft keystrokes are not logged (D-v); the submitted record is immutable and audited.
- **T3 A4 statuses:** a reassignment ends the old assignment with `revoked_at` instead of a new status, so the four statuses stay as specified.
- **T4 W2 and W4:** working modes remain as internal draft kinds (D-q). Users see tasks only.
- **T2 D-e:** the rename of `package_id` to `project_key` happens in T3a Task 1, as the T2 index foresaw. Stored payloads with `package_id` still load (`AliasChoices`); the v2 seed format keeps its field names (D-f).
- **T7 I5 and U3, sets per stage:** a stage done by one person contributes its `stage_result` set, which is that person's result under their pseudonym. It is not repeated as a separate `individual` set. Parallel annotate stages contribute one `individual` set per annotator.
- **T4 W1, applied early:** the language confirmation for manual assignments already applies in T3a.

## Risks

- **Rename churn (T3a Task 1):** the project-key rename touches the domain, about 40 test files, the OpenAPI contract and the frontend. It is mechanical and gated by grep checks, but it conflicts with any parallel branch.
- **ontospan 1.1 (T5 Task 1)** changes a second repository. The 1.0 schemas stay frozen, and the conformance suite must stay green there before Ontocurator re-pins.
- **Visibility leaks:** visibility is enforced in three functions (documents, annotation versions, comments). Each plan that adds a data path adds a "cannot see" test for it; a missing call is the most likely security bug.
- **Workflow state:** the per-document stage machine has many transitions (start, release, skip, insert, reopen, final). T4a keeps it a pure function with table-driven tests; the database only records its output.
- **Release set ids:** two import bundles may reuse an `annotation_set_id` for one document. The release builder refuses such a release with `RELEASE_SET_ID_COLLISION` and lists the sets instead of renaming them.
- **App.tsx size:** T3b moves the dashboard and the editor screen behind the router. Later frontend plans edit the new route components, not `App.tsx`.
- **Cross-plan file names:** T5, T4a and T4b name some T3 modules by role. Implementers extend the files the earlier plan actually created and never add parallel ones.
- **ontospan merge gate:** T5 Task 1 stops after opening the ontospan PR. Merging and pushing need the user's confirmation before T5 Task 2 can start.
